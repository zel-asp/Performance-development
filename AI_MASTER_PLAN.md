# AI Feature Master Plan
## Performance and Development Management System — Hotel and Restaurant Operations
### Consolidated: Scope, Limitations, Role Access, Workflow, Rate Limiting, Caching

This is the single reference document for every AI-related decision made for this system. It supersedes and merges: the Gemini boundary rule from the main build spec, the SBI Feedback Refiner feature plan, and the AI scope/limitations document. Use this as the one source of truth for both the coding agent and Chapter 1 documentation.

---

## 1. What the AI Does (Scope)

The system integrates the Gemini API for exactly **two functions** — nothing else is in scope unless this document is revised.

### 1.1 Realtime Sentiment Analytics
- Reads free-text already being generated by normal system use: coaching notes, evaluation comments, recognition messages.
- Produces a sentiment classification per submission.
- Aggregates sentiment at the department level for dashboard trend widgets.
- Passive only — never prompts or solicits input on its own.

### 1.2 SBI Feedback Refiner
- Accepts one supervisor-submitted rough observation (free text).
- Restructures it into a Situation-Behavior-Impact draft.
- Returns the draft for human review; never saves automatically.

### 1.3 Shared rule for both functions
Every AI output is either **read-only analytics** (sentiment trend) or an **editable draft requiring human approval** (SBI note). No AI output is ever committed to a permanent record without an explicit human action. All AI calls are logged (input reference, timestamp, requesting user).

---

## 2. What the AI Never Does (Limitations)

- Does not set or influence Performance ratings, Competency levels, Training pass/fail results, XP amounts, badge awards, or Succession readiness flags — all of these stay deterministic backend logic or explicit human input.
- Has no standing/persistent database access — each call is scoped to that single request's inputs only, with no memory across sessions.
- Cannot access another employee's records, payroll/personal data, or any other module's data (e.g., cannot pull Succession data while refining a coaching note).
- Provides no guaranteed accuracy — sentiment output is a probabilistic trend indicator, not a verified fact; SBI drafts are a starting point, not an authoritative account.
- Is not always available — if the API is down, rate-limited, or times out, every AI feature must degrade to its manual equivalent without blocking the underlying workflow.
- Is not tuned as a translation service and may lose quality on heavy Taglish/code-switching or highly specialized jargon outside general hospitality context — human review is required regardless.
- Does not replace the Employee/Supervisor/HR authority structure — it assists inside existing roles, it is not itself a decision-making role.

## 3. Role-Based Access Limits

This is the access boundary for each of the three system roles specifically with respect to AI features — separate from their general module permissions defined elsewhere.

### 3.1 Employee — most restricted

**Can:**
- Have their own submitted free text (self-assessment comments, goal notes) included as input to background sentiment analysis, the same as any other text in the system.
- (Pending adviser decision — see Section 6) potentially view SBI notes written about them, read-only, once those notes are finalized and surfaced in a formal appraisal discussion.

**Cannot:**
- Initiate any AI request. Employees have no access to the SBI Refiner — it is a Supervisor/HR tool only.
- View sentiment analytics dashboards or trend data, at either the individual or department level.
- Request AI refinement of their own self-assessments or goal statements. This is a deliberate design decision: self-assessments should reflect the employee's own unassisted voice, not an AI-polished version, to preserve the integrity of the appraisal input.
- See which of their submissions were flagged by sentiment analysis, or what score/classification was assigned.

### 3.2 Supervisor — scoped operational access

**Can:**
- Submit rough observations to the SBI Refiner for employees on their own team/department.
- Edit, regenerate, or discard AI drafts before saving.
- View aggregated sentiment trend data, but scoped only to their own department/team — not property-wide.
- Use the AI-assisted draft as one input among others when writing a coaching note; final wording and the decision to save are always the supervisor's own action.

**Cannot:**
- Submit observations about employees outside their own team/department.
- Bulk-generate SBI drafts for multiple employees in a single request — the tool is single-observation, single-employee per submission, by design (prevents mass-generated, low-quality coaching notes).
- View sentiment data for other departments or property-wide aggregates (that visibility is HR-only).
- Treat an AI-generated sentiment flag or SBI draft as sufficient justification on its own for a formal rating, disciplinary action, or promotion decision — those still require the normal calibration/review process.
- Exceed the per-user rate limit (Section 4) — no role-based override or bypass exists for supervisors, including urgent/high-volume shift periods.
- Use the SBI Refiner to draft formal disciplinary or legal documentation. If a coaching observation escalates into a disciplinary matter, that documentation should be handled through HR's normal process, not the AI drafting tool.

### 3.3 HR — broadest, but still bounded

**Can:**
- View sentiment trend data aggregated property-wide, across all departments.
- Use the SBI Refiner for any employee, not scoped to a single team (HR's oversight role justifies this wider scope).
- Access the AI request audit log for compliance review.

**Cannot:**
- Override the requirement for human review/approval on any AI draft — HR's broader visibility does not grant an auto-approve or auto-save capability.
- Use AI output to directly set a Succession readiness flag, competency score, or rating — HR's manual calibration step (defined in the Succession Planning workflow) remains a required human action regardless of any AI signal.
- Bypass the rate limit structure — HR accounts are subject to the same caps as supervisors, sized appropriately for HR's broader usage pattern but not unlimited.

---

## 4. Rate Limiting

- Each user (Supervisor or HR) is capped at a fixed number of AI-assisted requests per time window (e.g., 20/hour, 100/day — tune against real shift volume, confirm with adviser rather than guessing a final number).
- Enforced via a request-count table or cache store keyed by `user_id` + time bucket.
- On limit reached: reject with a clear message and a retry time; never fail silently.
- The manual (non-AI) path for every feature always remains available — hitting the rate limit never blocks the underlying workflow (e.g., a supervisor can still type and save a plain coaching note without AI refinement).
- Rate limiting exists primarily for cost control, secondarily for abuse prevention — this is a real cost lever, not just a technical safeguard.

---

## 5. Caching

**Do not cache:** actual SBI drafts or sentiment scores. Each submission is realistically unique; caching risks returning a stale or mismatched result for a different real event.

**Do cache:**
- The two static demo scenario chips (`Rush Hour Composure`, `Sommelier Upsell Win`) — fixed example text, cache the generated output once, no TTL needed since input never changes.
- The system prompt/instruction template — keep as a static constant in code rather than rebuilding per call.

**Failure fallback:** if the Gemini call fails or times out, return the user's original raw input with a note that AI assistance is temporarily unavailable, and let them proceed manually. AI success is never a precondition for completing the underlying task.

## 6. UI/UX Design Process for Interactive AI Integration

This section defines how to design the *interaction*, not just the backend logic, for both AI features. The goal is a UI that makes AI assistance feel like a fast, optional aid a supervisor reaches for mid-shift — never a black box, and never something that slows down or blocks the core task.

### 6.1 Design principles (apply to every AI touchpoint)

- **AI content is always visually distinct from human content.** A saved coaching note that was AI-refined must look different at a glance from one that was typed manually — a label, a subtle badge, or a color accent, not just metadata buried in a details view.
- **Every AI output is a draft until a human acts on it.** The UI must never present AI text as if it's already saved. Use language like "Suggested SBI Draft" rather than "Your Coaching Note," until the supervisor explicitly saves.
- **Reversibility over confirmation dialogs.** Favor letting the supervisor freely edit or regenerate over popping up "Are you sure?" modals — friction should come from *editing being easy*, not from gatekeeping with alerts.
- **Show effort, not internals.** While Gemini is processing, show a short, honest loading state (e.g. "Structuring your note...") — never expose raw model reasoning, confidence scores, or technical errors to the end user.
- **Fail visibly, not silently.** If the AI call fails, say so plainly and immediately hand control back to manual input — don't leave the supervisor staring at a stuck spinner.
- **Design for the floor, not the office.** Supervisors will likely use this on a tablet or phone between shift tasks, often standing, sometimes one-handed. Prioritize large tap targets, minimal typing, and the ability to fully abandon the flow in one tap.

### 6.2 Step-by-step design process

1. **Map the trigger points first.** For each AI feature, identify exactly where in the existing screen flow it's invoked (e.g., a "Refine with AI" button next to the existing free-text coaching field — not a separate standalone page). The AI entry point should sit beside the manual path, never replace it.
2. **Design the idle/empty state.** What the field looks like before any AI action — this is where the two demo scenario chips (`Rush Hour Composure`, `Sommelier Upsell Win`) live, giving a new user a one-tap way to see the feature work before trusting it with a real observation.
3. **Design the processing state.** Short, honest loading feedback (per 6.1). Keep this under a few seconds where possible — if Gemini's response time runs long, the caching/static-template optimizations in Section 5 exist partly to keep this state brief.
4. **Design the draft/review state.** This is the highest-stakes screen. Show the three SBI fields (Situation/Behavior/Impact) as separately editable, not one merged block — a supervisor should be able to fix just the "Impact" line without retyping the whole note. Clearly label it as AI-generated and unsaved.
5. **Design the action row.** Three clear actions, equally weighted, no default/pre-selected button: **Edit**, **Regenerate**, **Discard**, plus a distinct **Save** action that's visually separated from the drafting actions so it can't be tapped by accident.
6. **Design the saved/committed state.** Once saved, the note should visually shift out of "draft" styling into whatever the standard coaching-note display looks like elsewhere in Performance Management — with the `source: ai_refined` tag preserved but de-emphasized, so it reads as a normal record, not a permanently flagged AI artifact.
7. **Design the failure and rate-limit states explicitly** — don't leave these as an afterthought. A rate-limit hit should look like a normal, calm message with a retry time and a visible manual-entry option, not an error page.
8. **Design the sentiment trend widget separately from the drafting UI.** This is a passive dashboard element (per Section 1.1), not an interactive tool — keep it as a simple trend indicator (e.g., a small line or color-coded badge per department) rather than exposing granular per-submission scores, which would encourage over-reading individual data points.

### 6.3 Usability validation before finalizing

- Test the SBI Refiner flow with someone who has actually done floor supervision (or the closest available proxy), not just other developers — the value of this feature depends entirely on whether real coaching language feels natural, which is hard to judge from a dev chair.
- Specifically test: can a first-time user tell, without being told, which parts of the screen are AI-generated versus their own input? If not, revisit the labeling from 6.1 before moving on.
- Check the flow on an actual small screen/tablet, not just a resized browser window — line wrapping and tap-target sizing behave differently on real touch devices.

## 7. Open Decisions Requiring Adviser Sign-off

1. **Employee visibility of SBI notes** — read-only access once finalized, or supervisor/HR-facing only? This affects both the database visibility flag design and the UI.
2. **Exact rate limit numbers** — the figures above (20/hour, 100/day) are placeholders sized for a reasonable hotel property; confirm against expected real usage before hardcoding.
3. **Taglish/code-switched input handling** — decide whether to add a disclaimer in the UI when input appears heavily localized, or leave this as a known limitation documented in Chapter 1 without special UI handling.

---

## 8. Data Model Summary

- `coaching_notes`: id, employee_id, supervisor_id, situation, behavior, impact, source (`ai_refined` / `manual`), visibility flag (per Section 6.1), created_at
- `rate_limits`: user_id, window_start, request_count
- `ai_request_log`: id, user_id, feature (`sbi_refiner` / `sentiment`), input_reference, timestamp — for the audit trail referenced in Section 1.3 and HR's compliance access in Section 3.3
- Demo chip cache: static config entry, not a database table

---

## 9. Summary Statement (for Chapter 1 — Scope and Limitations)

> The system integrates the Gemini API strictly as an assistive layer, supporting two functions: realtime sentiment analysis of existing free-text inputs, and structured feedback/reflection draft generation. Access is available across roles — Associates can use the AI Copilot for personal shift reflection and constructive peer feedback, Supervisors are scoped to coaching subordinates in their own department, and HR has property-wide visibility, all subject to the same per-user rate limits and human-approval requirements. The AI does not calculate scores, set ratings, assign points, or determine succession or promotion outcomes; all such decisions remain governed by deterministic system logic or explicit human authorization. This boundary was a deliberate design decision to keep the system auditable and ensure AI involvement supports, rather than replaces, human oversight in people-management decisions.
